# Multi-Agent Cyber-Threat Detection and Response (CrewAI + RAG)

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/shreyaaaa27/SOC_RAG/blob/main/notebooks/Cyber_Threat_Detection_CrewAI_RAG.ipynb)

An educational demo of an AI-assisted Security Operations Centre (SOC) workflow. A deterministic Python rule engine detects simulated attacks in labelled security logs. Four CrewAI agents then explain the detections, map them to MITRE ATT&CK using retrieval-augmented generation (RAG), draft recommended responses, and write an incident report.

> **Scope:** all log data is **synthetic** and generated in the notebook. The agents only **recommend** actions; nothing is blocked, isolated or remediated. This project is a learning exercise in multi-agent orchestration and RAG, not a production security tool.

---

## How it works

```
data/security_logs.csv ─► Rule engine (7 rules) ─► tool: analyze_security_logs
                                                        │
Knowledge base (20 docs: MITRE ATT&CK summaries + playbooks)
  ─► all-MiniLM-L6-v2 embeddings ─► FAISS ─► tool: search_threat_intel   (RAG)
                                                        │
        CrewAI, sequential process, Gemini LLM:
        Log Analyst ─► Threat Intel Analyst ─► Incident Responder ─► Report Writer
                                                        │
                                       Markdown incident report (recommendations only)
```

| Component | What it does |
| :-- | :-- |
| **Synthetic logs** | 455 events in one hour: 300 benign and 155 malicious across 7 attack types. Generated with a fixed random seed, with a ground-truth `label` on every row. |
| **Rule engine** | Seven rules: brute force (≥10 failed logins in 5 min), port scan (≥20 distinct ports), SQL-injection signatures, C2 beaconing (≥10 outbound connections with interval std < 5 s), large outbound transfers (>100 MB), privilege change by a non-admin user, and look-alike phishing domains. |
| **RAG** | 20 short hand-written documents (MITRE ATT&CK technique summaries, response playbooks, severity policy). Embedded with Sentence-Transformers `all-MiniLM-L6-v2` (384 dimensions) and searched by cosine similarity in a FAISS `IndexFlatIP`, top-3 results. |
| **Agents** | Log Analyst (calls the rule engine), Threat Intel Analyst (RAG search), Incident Responder (RAG search over playbooks), Report Writer. Each agent runs as its own step and receives the saved outputs of the steps it depends on, so a failed step can be retried without repeating earlier ones. |
| **Live demo** | A two-agent crew that assesses any new alert text, separating observed facts from hypotheses. |

**Why rules plus agents?** LLMs are unreliable at counting and thresholding hundreds of rows. The rules give repeatable, testable detections; the agents add explanation, mapping and drafting on top.

## Run it in Google Colab

### 1. Get a Gemini API key
1. Open [Google AI Studio](https://aistudio.google.com/apikey) and sign in.
2. Click **Create API key**. The free tier is enough for this demo, but it has rate limits.

### 2. Store the key in Colab Secrets
Never paste the key into a notebook cell.
1. Open the notebook in Colab using the badge above.
2. Click the **🔑 Secrets** icon in the left sidebar, then **Add new secret**.
3. Set **Name** to `GEMINI_API_KEY` and **Value** to your key.
4. Turn on **Notebook access**.

The notebook reads the key with `google.colab.userdata.get("GEMINI_API_KEY")` and never prints it.

### 3. Run
1. Run the first cell, which installs the libraries.
2. If Colab shows **Restart session**, click it.
3. Choose **Runtime → Run all**.

What to expect:
- The connection cell prints which Gemini model it is using. It tries several Flash model IDs in turn, because model names change over time and each model has its own daily free-tier quota.
- Each agent runs as a separate step and its output is saved. If a step fails (for example a temporary `503` overload), **re-run the pipeline cell**: finished steps are skipped and it continues from the failed step. Temporary errors are retried automatically after 90 seconds.
- If the model's **daily** free-tier quota is used up, the cell stops immediately instead of wasting retries. Re-run the connection cell to move to the next model, then the cells below it.
- Iteration caps (`max_iter`) and a limit on search calls keep a full run plus the live demo to roughly 15–20 requests. That fits the free tier, which can be as low as 20 requests per model per day.

The notebook writes `security_logs.csv` and `soc_incident_report.md` to the Colab working directory.

**Running locally (optional):** install `requirements.txt`, set the environment variable `GEMINI_API_KEY`, and run the notebook in Jupyter. The install cell and the top-level `await` are written for Colab and Jupyter.

## Sample results

**Rule engine on the synthetic dataset** (event level, 455 events):

| | Precision | Recall | F1 | Support |
| :-- | :-: | :-: | :-: | :-: |
| Benign | 1.000 | 1.000 | 1.000 | 300 |
| Malicious | 1.000 | 1.000 | 1.000 | 155 |

Every attack type was detected (100% per type), with 0 false positives and 0 false negatives.

> ⚠️ **These numbers are not a real-world detection rate.** The attacks were generated to match the rules, so a perfect score only shows that the pipeline is wired correctly. Real logs would produce false positives and need threshold tuning.

**Detections:**

| Threat | Severity | Source | Evidence (summary) |
| :-- | :-- | :-- | :-- |
| Brute force | CRITICAL | 185.220.101.45 | 45 failed SSH logins for `admin`, then 1 success |
| C2-like beaconing | CRITICAL | 10.0.0.23 | 30 connections to port 4444 about every 60 s |
| Large outbound transfers | CRITICAL | 10.0.0.23 | about 2.0 GB in 4 transfers to the same external IP |
| Privilege escalation | CRITICAL | 10.0.0.31 (`intern01`) | 2 failed `sudo`, then root via a logged CVE-2021-4034 exploit |
| SQL injection attempts | HIGH | 91.240.118.22 | 10 requests with `OR '1'='1`, `UNION SELECT`, `SLEEP()` payloads |
| Phishing site visit | HIGH | 10.0.0.17 (`meera`) | GET and POST to a look-alike Microsoft login domain |
| Port scan | MEDIUM | 203.0.113.77 | 60 distinct ports in 59 s, all rejected |

**Agent outputs** (run of 21 Oct 2026, `gemini/gemini-3.5-flash-lite`; all four steps completed in about 25 s):
- [`reports/soc_incident_report.md`](reports/soc_incident_report.md) is the Report Writer's unedited output, with reviewer notes. It labels the data as simulated and the actions as recommendations, separates facts from hypotheses, and marks uncertain MITRE mappings (T1071, T1041) as tentative. The notes list what is still imperfect: the timeline is not in chronological order, two mappings marked "Direct" should be tentative, and some hosts are called "compromised" before verification.
- [`reports/live_demo_alert_assessment.md`](reports/live_demo_alert_assessment.md) is the live-demo answer for a hypothetical email-attachment alert. It separates observed facts from hypotheses and recommends verification steps before containment.

**Before and after.** The first run's report overstated the evidence: it said the SOC had already responded, called the transferred data "sensitive", and presented the activity as confirmed compromise. Its live-demo answer treated file execution as fact. Both are kept, with manual corrections, in [`reports/first_run_report_corrected.md`](reports/first_run_report_corrected.md) and [`reports/first_run_live_demo_corrected.md`](reports/first_run_live_demo_corrected.md).

Reviewing the first run led to two notebook changes:
- every task prompt now has explicit evidence rules (facts vs. hypotheses, tentative mappings, recommendations only);
- four knowledge-base documents were added, because the demo alert's best match had been a weak, irrelevant document (similarity 0.28). In the second run, the demo's top matches were relevant (0.38 and 0.63).

## Limitations
- **Synthetic data.** The logs and attacks are hand-designed, and the rule thresholds are static and tuned to them.
- **Small knowledge base.** It has 20 short hand-written summaries, not the full MITRE ATT&CK dataset. Retrieval quality was checked by inspection, not measured.
- **LLM variability.** Outputs change between runs and can overstate evidence even with careful prompts. Reports need human review, and report quality was not scored with a metric.
- **Free-tier limits.** Gemini rate limits make runs slow, and they can fail during busy periods.
- **No real actions.** The system produces recommendations only, by design.

## Future work
- Evaluate on public labelled data (for example CIC-IDS2017, or Zeek/Sysmon samples) and report false positives.
- Load the full MITRE ATT&CK STIX data into the vector store and measure retrieval with recall@k on labelled queries.
- Add an anomaly-detection model (for example Isolation Forest) for attacks the rules do not cover.
- Have agents return structured JSON validated against a schema, and add a human-approval step before any automated response.
